# Week 1 — Web3 向进阶：比较 EOA、智能账户、多签的权限差异

> 目标：理解三类以太坊账户的安全边界、控制权模型与适用场景，不涉及实际创建操作。

---

## 一、总览对比表

| 维度 | EOA（外部账户） | 智能账户（ERC-4337） | 多签账户（如 Safe） |
|------|:--------------:|:-------------------:|:------------------:|
| **控制权归属** | 私钥持有者（单一实体） | 合约代码定义的规则 + 所有者签名 | M-of-N 签名者群体 |
| **谁能发起交易** | 私钥持有者直接用私钥签名 | 所有者签名 UserOperation → Bundler 代为提交 | 任一方签名方提出提案，达到 M 人确认后上链 |
| **多人确认** | 不支持（一人一钥） | 可编程支持（合约内实现 M-of-N） | 原生支持（M-of-N 阈值） |
| **恢复机制** | 无 — 丢失私钥 = 永久失去资产 | 支持社交恢复、时间锁替换所有者 | 支持替换签名者（需达到阈值） |
| **限额策略** | 无 — 每次交易全额可用 | 可编程（日限额、单笔限额、白名单） | 可编程（花费限额、延时执行） |
| **自动化策略** | 无 — 每笔交易必须手动签名 | 支持（定期付款、条件触发） | 支持（时间锁、批处理、委托调用） |
| **Gas 支付** | 发起者用 ETH 支付 | 支持代付（paymaster 用 ERC-20 或第三方代付） | 发起者或任一签名方支付 |
| **典型场景** | 个人日常钱包、DeFi 交互 | 新手友好钱包（免助记词）、企业日常支出 | DAO 金库、团队共管资金、协议多签 |
| **主要风险** | 私钥丢失/泄露 = 全部资产归零 | 合约代码漏洞、升级权限被滥用 | 签名方串通/被挟持、协调失败（达不成阈值） |
| **需人工确认的操作** | 每一笔交易 | UserOperation 签名、恢复/修改所有者 | 提案需 M 人各自签名；执行后自动上链 |

## 二、逐类详解

### 1. EOA（Externally Owned Account）— 外部账户

**一句话**：一个私钥 = 一个账户 = 全权控制。私钥在哪，资产就在谁手里。

**安全边界**：
- 控制权和风险全在私钥持有者一人身上.
- 所有操作都必须用私钥签名，链上无法区分「被盗」和「本人操作」——签名即授权，不可逆。

**适用场景**：
- 个人日常钱包（MetaMask 创建的默认账户就是 EOA）
- 高频 DeFi 交互（swap、借贷、质押），因为每笔 gas 最低、延迟最小

**风险点**：
- 私钥丢失 = 资产永久冻结，无人能恢复
- 私钥泄露（钓鱼网站诱导签名 / 助记词被截屏） = 资产瞬间被转走，无法冻结或追回

**需要人工确认的操作**：**全部**。EOA 无链上程序化执行能力——私钥签名即授权，没有任何链上规则（限额、延时、多签）来拦截或约束交易。每一笔交易的生效都必须链下私钥主动签名，安全策略完全依赖私钥的保管方式。

---

### 2. 智能账户（Smart Account / ERC-4337）

**一句话**：账户不是一把私钥，而是一段合约代码。你签名的是一个「操作意图」，不是原始交易。

**要解决什么样的问题**: 
| EOA 的问题 | ERC‑4337 的解决方式 |
|-----------|----------------------|
| 单一私钥、丢失即毁灭 | 可编程验证、多签、社交恢复 |
| 合约不能主动发起交易 | UserOperation + EntryPoint 让合约能“像账户一样行动” |
| 必须用 ETH 支付 Gas | Paymaster 支持代币支付或免 Gas |
| 无法批处理操作 | 支持 batched calls |
| 无法升级、无扩展性 | 智能账户可升级、可模块化 |
| 无法表达复杂权限 | 自定义权限、session key、限额等 |

**核心架构**：ERC-4337 不在以太坊共识层动手脚，而是靠**链上合约 + 链下基础设施**实现：

```
ERC-4337 交易：
  你 → 签名 UserOperation（操作意图）
       ↓
      Bundler（打包节点）→ 批量提交到 EntryPoint 合约
       ↓
      EntryPoint → 验证 → 调你的智能账户合约 → 执行
```
UserOperation: 对智能账户授权做某件事情.但具体怎么执行、谁来付 gas，由合约和 Bundler 决定
| 角色 | 干什么 |
|------|--------|
| **你的智能账户** | 链上合约，定义你账户的规则（谁可以花钱、限额多少、怎么恢复） |
| **EntryPoint** | 全局单例合约，负责验证和执行所有 UserOperation |
| **Bundler** | 链下节点，打包多条 UserOp 批量提交（类似区块构建者，任何人可运行） |
| **Paymaster** | 代付 gas 的合约——可用 ERC-20 付 gas，甚至第三方替你付

**安全边界**：
- 逻辑写在合约里，签名方（Owner）只是触发者之一。合约可以规定：每日最多花 1 ETH、转账到陌生地址需等 48 小时、Owner 被替换需 3 个守护者（Guardian）同意。
*Guardian*: 我提前指定的一组"人", 收集起来这些签名就可以替换账户的私钥
- 钱包代码可升级，意味着修复漏洞的能力，也意味着被恶意升级的风险。

**适用场景**：
- 新手或非技术用户——通过社交恢复避免助记词丢失导致的资产全损
- 企业日常支出——设置员工每日限额，超出限额自动拒绝
- 自动化定投/定期付款——合约定时执行，无需人工每笔签字

**风险点**：
- 合约漏洞：智能钱包代码有 bug（如重入漏洞、权限绕过），攻击者可绕过规则直接提走资金
- 升级权限集中：如果 Owner 或 Recovery 机制被攻破，攻击者可把自己设为唯一 Owner 并提取所有资产

**需要人工确认的操作**：
- 签名 UserOperation（相当于「批准意图」）
- 修改所有者、添加恢复守护者

### 3. 多签账户（Multi-signature Account，如 Safe）

**一句话**：N 个人共同管一个账户，至少 M 个人同意才能动里面的钱。一个人说了不算。
现在多签可以当作智能账户的子集
**安全边界**：
- 控制权分散在多个独立签名方之间，单点私钥泄露不会导致资产损失（攻击者还需要攻破 M-1 个签名方）。
- 安全层级高，但协调成本也高——签名方不可用或拒绝配合时，资产可能被「锁死」无法动用。

**适用场景**：
- DAO 金库管理：5 个核心成员管金库，3/5 阈值，任一人叛变也无法单方面转走资金
- 协议治理合约 Owner：Uniswap、Aave 等协议的升级权限交给 4/7 多签，防止单方恶意升级
- 团队共管资金：两人合伙钱包，2/2 阈值，任何支出需双方确认

**风险点**：
- 签名方协调失败：1/3 签名方永久失联 → 账户变成 2/3 → 仍可操作；但如果阈值刚好无法达成（如 2/3 变为 1/3 剩余签名者），资产就被永久锁定
- 签名方群体被挟持：如果 M 个签名方同时被社工/胁迫，攻击者可在一次操作中清空金库

**需要人工确认的操作**：
- 发起提案
- 每个签名方对提案的确认签名
