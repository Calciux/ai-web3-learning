# Week 2 | 模块 A：问题空间与方向地图

> 目标：快速看完整个 AI × Web3 的几大交叉领域，再选择一个主方向深入。

## 一句话

AI × Web3 不是把两个 buzzword 拼在一起——真正有价值的问题落在**"机器执行 + 经济交换 + 权限控制 + 可验证记录"**的交界处。一个方向是否成立，不看它用了多少新词，而看 AI 能力和 Web3 机制是否**同时不可替代**。

## 统一判断框架

每个方向都用同一组 7 个问题判断：

| # | 问题 | 考察维度 |
|:-:|------|:--------:|
| 1 | **没有 AI，这个方向是否仍然成立？AI 承担什么能力？** | AI 是否不可替代 |
| 2 | **没有 Web3，这个方向是否仍然成立？Web3 提供什么机制？** | Web3 是否不可替代 |
| 3 | **谁发起任务、执行、付款、验收、承担失败成本？** | 角色与权责分配 |
| 4 | **哪些动作可自动化？哪些必须人工确认？** | 自动化边界 |
| 5 | **结果如何验证？验证成本是否低于人工协调成本？** | 可验证性 |
| 6 | **它更像应用层体验、开发者工具、协议/标准、权限系统、安全机制、还是治理协作？** | 落地层 |
| 7 | **如果失败，最可能原因是什么？** | 风险预判 |

## 开始速览

### Direction 1：Payment / Commerce / Settlement
#### 我的判断

**Agent 经济活动如何形成可控闭环**。AI Agent 在链路中不止是自动化的手，更是做判断的脑：识别需求→选择服务方→验证交付物→触发结算或争议。它的价值不是替代人类的脏活，而是**在明确授权边界内做适应性判断**——读取上下文、处理不确定性、在规则允许范围内做决策。

#### 一句话

Agent 经济活动不是普通支付的简单延长。真正困难的是把**发现服务 → 报价 → 授权预算 → 执行任务 → 交付结果 → 验收判断 → 付款/退款/争议**连成一个可控链路。AI Agent 在预算和权限边界内做到更多——不只是「能转账」，而是能理解买的是什么、判断交付是否合格、在不合格时触发正确的结算分支。Web3 提供链上托管、不可篡改的收据和可验证的执行记录，让每一步都有据可查、不可抵赖。

#### 三问

- **解决什么真实问题？** Agent 作为消费者或服务提供者时，需要明确预算、支付条件、交付标准和失败补救。不是「能不能转账」——传统支付已解决。真正的痛点：(1) Agent 买的东西千差万别（API 调用、数据查询、计算任务、内容生成、链上执行），不同服务需要不同的验收方式；(2) 交付能否被自动验证？不能自动验证时，谁来验收、标准是什么？(3) 报价→执行→验收→结算如何形成闭环，每一环都有可追溯记录；(4) 争议时钱归谁、按什么规则裁决？
- **AI 角色？Web3 角色？** AI：理解用户意图→识别需要什么服务→在授权范围内选择服务方→验证交付质量→触发结算或争议。Web3：提供链上托管（ERC-8183：资金在验收通过前双方都不能单方面动）、不可篡改的收据与执行记录（链上状态变更+事件日志）、可编程权限边界（CAW Pact：限制金额/合约/时间窗口）。分工：AI 做判断和适应，Web3 做执行约束和记录留痕。
- **落地层？** 课程模块 B 的四层框架：**场景层**——明确 Agent 买的是什么（API/数据/算力/内容/链上执行），不同服务决定不同验收方式。**流程层**——画完整链路图（发现→报价→授权→执行→交付→验收→付款/退款/争议）。**验证层**——判断交付能否自动验证；不能的话谁来验、标准是什么、争议怎么处理。**协议层**——需要哪些底层标准（checkout/invoice/receipt/escrow/evaluator/reputation/marketplace）。协议层是多标准共存，不是择一——ERC-8183 管托管状态机，ERC-8004 管跨交易声誉聚合（Dir2 的基础设施，但协议层引用），x402 管机器支付触发。当前最成熟的是协议层（多个 EIP 在推进），最薄弱的是应用层——还没有「Agent 版淘宝」。

#### 7 问评估

| # | 问题 | 回答 |
|:-:|------|:----|
| 1 | **没有 AI？** | 仍然成立——人可以手动发包、比价、验收。但 AI 提供三个不可替代的能力：(1) 不同服务需要不同验收方式，AI 可根据任务类型自适应生成验收标准；(2) 7×24 独立验收——人做 Evaluator 是瓶颈；(3) 在授权边界内做适应性判断——不只是执行规则，而是理解上下文后决定下一步。没有 AI，commerce 的「适应性」退化为「脚本式自动化」 |
| 2 | **没有 Web3？** | 部分成立——传统支付（Stripe/Escrow.com）可以提供结算和托管。但 Web3 提供传统金融做不到的三点：(1) 无许可托管——任何 Agent 无需 KYC/银行开户，部署合约即可接入托管（ERC-8183）；(2) 链上收据不可篡改——验收结果和结算记录一旦上链无法被任何一方删除或修改；(3) 可组合性——托管合约可与 Dir3 的权限层（CAW Pact）和 Dir2 的声誉层（ERC-8004 Hook）组合。传统 Escrow 是封闭产品，链上托管是可编程积木 |
| 3 | **角色分配？** | 用户→设定预算边界（金额/合约/时间窗口）、处理争议升级。Agent（消费者）→识别需求、选择服务方、授权下单、验证交付。服务方 Agent→返回报价、执行任务、交付结果。托管合约（ERC-8183）→管理资金状态机（Open→Funded→Submitted→Completed/Rejected），确保双方都不能单方面动钱。Evaluator→独立验收交付质量（可以是 LLM/合约/人——Dir1 的验收角色，不是 Dir2 的声誉系统）。CAW→提供权限边界（Pact 限制 Agent 能花多少、在哪花）。失败成本：服务方不达标→退款；Agent 不付款→服务方不交付；Evaluator 误判→A 或 B 受损（最大风险，需 Dir2 声誉体系辅助缓解） |
| 4 | **自动化 vs 人工？** | 全自动：Budget 内小额付款、已验证服务方、重复性采购、可程序化验收的标准交付物。需人工：首次授权、超预算操作、新服务方首次交易、争议升级。核心原则：验收标准和预算边界由人设定，边界内的操作 Agent 自主执行，边界外的操作自动拒绝或升级人工 |
| 5 | **如何验证？** | 课程模块 B 三层：**支付层**——链上收据+报价签名对比（成本极低）。**交付层**——可程序化验证的直接跑逻辑；不可程序化的引入 Evaluator（LLM/合约/人）做独立判断。**记录层**——验收结果和结算记录一旦上链不可篡改，任何第三方可事后复查 Evaluator 的判断理由。核心优势不是比人工协调更便宜，而是**不可抵赖**——链上记录让纠纷有据可查 |
| 6 | **落地层？** | 课程四层框架：**场景层**（明确买什么）→ **流程层**（画完整链路）→ **验证层**（设计验收和争议逻辑）→ **协议层**（选底层标准：ERC-8183 托管状态机 / x402 支付触发 / ERC-8004 跨交易声誉（Dir2 基础设施在此引用）/ CAW Pact 权限边界）。协议层多标准共存，按需组合。最成熟的是协议层，最薄弱的是应用层——还没有「Agent 版淘宝」 |
| 7 | **失败原因？** | 四个风险：(1) Evaluator 误判——LLM 验收标准不稳定，同一交付物两次判断可能不同。缓解：用具体 checklist 而非开放式评判，验收理由公开可复查。(2) 用户不敢让 Agent 自动花钱——需要成功案例建立信任。(3) L1 gas 太高让微支付不可行——需 L2 缓解。(4) 标准碎片化——ERC-8183/8004/x402/MPP 各管一段，尚无统一整合层 |

### Direction 2：Identity / Reputation / Capability / Interoperability
#### 我的判断

解决了web3如何为Agent提供服务使其更可信的问题,构建信任基座.

#### 一句话

Agent 需要一个可验证的身份才能被信任——谁拥有它、它能做什么、怎么调用它、历史声誉如何。没有身份，Agent 之间无法建立长期信任；没有声誉，用户无法判断哪个 Agent 值得付款；没有可互操作的能力声明，Agent 无法自动发现和调用彼此。身份、声誉、验证三者共同构成 Agent 经济的信任底座。

#### 三问

- **解决什么真实问题？** 四个嵌套问题：(1) 发现——用户和 Agent 如何找到能完成特定任务的服务 Agent？需要可查询的 Agent 注册表；(2) 评估——如何判断一个 Agent 是否可信？声誉必须按任务类型评分、有时间衰减、绑定链上证明不可伪造；(3) 能力声明——Agent 的能力描述必须机器可读，否则无法自动发现和调用；(4) 互操作——不同框架构建的 Agent 如何互相调用？需要统一的通信标准和验证方式。
- **AI 角色？Web3 角色？** AI：提供自我描述——身份声明、能力声明、服务端点。但 AI 的输出本身不可信——任何 Agent 都可以声称自己"擅长审计"。Web3：提供三根信任锚——不可篡改的注册表、可验证的声誉（链上评分不可删除）、组合式验证层（第三方验证者输出链上证明，调用方可自由选择信任谁）。
- **落地层？** 协议/标准层（身份/声誉/验证三个注册表）+ 链下聚合与发现层（声誉计算算法、Agent 搜索引擎）+ 应用集成层。Dir2 更接近基础设施层，被其他五个方向共同依赖。

#### 7 问评估

| # | 问题 | 回答 |
|:-:|------|:----|
| 1 | **没有 AI？** | N/A.此方向本身是Web3的trustless能力赋予Agent. |
| 2 | **没有 Web3？** | 传统 AI 生态也有评分和排行榜，但做不到：无许可注册（任何 Agent 可自主注册）、不可篡改的声誉（评分无法被平台删除）、可组合的验证（调用方可自由选择信任哪些验证者）、跨平台互操作（身份可在不同链和应用间携带）。 |
| 3 | **角色分配？** | Agent Owner→注册 Agent Profile、更新能力声明、处理争议。Client→查询注册表发现 Agent、查询声誉评估可信度、请求第三方验证、提交使用反馈。第三方验证者→运行验证逻辑输出链上证明，作弊则 stake 被 slashing。Registry 合约→不可篡改的存储层。失败成本：Agent 虚假声明→声誉下降+用户流失；验证者作弊→stake 被 slash；Client 被虚假 Agent 欺骗→自行承担损失（Dir2 提供信任信号而非保险）。 |
| 4 | **自动化 vs 人工？** | 全自动：身份注册、能力声明更新、反馈上链、验证请求/响应。需人工：身份所有权转移、高价值验证仲裁、争议处理。终极目标是让"是否信任一个 Agent"这个决策也自动化——基于链上声誉+验证记录的程序化判断。 |
| 5 | **如何验证？** | 三层：身份验证（查询所有权+端点可达性，成本极低）、声誉验证（查询历史反馈+链下聚合计算，成本中等）、能力验证（zkML 证明/TEE 远程证明/staker 重跑验证，成本因方案而异）。原始反馈全部链上可查——任何人可用自己的算法重新计算声誉。 |
| 6 | **落地层？** | 课程模块 C 指出 MCP、A2A、ERC-8004、MPP 不是同一种东西，处在不同层级：**工具协作层**（MCP — Agent 与工具/数据源之间的接口）、**Agent 协作层**（A2A — Agent 与 Agent 之间的任务通信）、**链上信任层**（ERC-8004 — 身份/声誉/验证三个注册表，是链上基础设施）、**支付层**（MPP — 机器支付协议）。Dir2 的核心在链上信任层（ERC-8004），但需要理解这四层各自解决什么、不能混为一谈。以及：ENS/DID 解决命名与身份声明，EAS 解决链上 Attestation，它们都在 Dir2 的工具箱里但层级不同 |
| 7 | **失败原因？** | 最大风险：信任不可建——声誉可刷（Sybil 攻击创建大量假身份互相好评）、验证者合谋、链上声誉与链下实际服务质量脱钩。Agent 没有"人的唯一性"，恶意 Actor 可创建海量 Profile。其次：冷启动问题（新 Agent 无声誉永远无法获得初始信任）、接口不成熟（标准仍在讨论中）。 |


### Direction 3：Wallet / Permission / Safe Execution
#### 我的判断
执行边界范畴的概念.被授权的对象从可信实体变成了概率系统,难点即在于此.风险在工程上和用户的风险偏好难以折中.

#### 一句话

Agent 不可以接触主私钥——Agent 只能拿到可验证、可限制、可撤销的行动空间。技术栈由 Smart Account（账户以合约规则表达权限）、Session Key（临时受限钥匙，约束时间/合约/额度/可撤销性）、Policy Engine（任务级权限与确定性拦截）、Guard（拒绝越界动作）、Simulation（预演交易结果）、多层 Revocation（随时收回权限）组成。核心理念：Agent 不应该拥有无限支付能力，只应该拿到具体任务、预算和收款方范围内的支付权限。

#### 三问

- **解决什么真实问题？** Agent 需要执行链上操作，但不能拥有无限权限。问题不是"AI 会不会花钱"，而是"AI 能在什么范围、额度、条件下花钱——以及如何立刻停下来"。AA Wallet 让账户表达规则而非仅靠私钥，Smart Account 提供可编程执行边界，Safe 的多签让 Agent 参与流程而非单独控制，Session Key 是一组受限能力而非"小号私钥"。
- **AI 角色？Web3 角色？** AI：在授权范围内生成交易草稿、请求执行低风险操作——但它是不受信任的概率组件。Web3：提供可编程权限基础设施——Smart Account 承载规则、Session Key 表达临时授权、Policy 定义可检查规则体系、Guard 做确定性拦截、Simulation 预演结果、MPC 分布式签名。分工原则：Agent 生成候选，Guard 强制执行边界。
- **落地层？** 协议标准层（Account Abstraction + Session Key 标准）+ 产品层（Cobo Agentic Wallet 的 Pact + Policy Engine + MPC、Safe 多签 + Guard）+ 辅助层（Simulation + Revocation + Human Check 分层确认）。

#### 7 问评估

| # | 问题 | 回答 |
|:-:|------|:----|
| 1 | **没有 AI？** | N/A. 有了AI agent的参与才会出现这个问题. |
| 2 | **没有 Web3？** | N/A. 这个方向是向Web3引入AI Agent带来的亟需解决的问题. |
| 3 | **角色分配？** | 用户→设定 Policy（每日上限、白名单合约、滑点阈值）、批准 Pact（任务目标+预算+收款方范围）、随时撤销。Agent→在授权内生成候选，但其输出被视为 untrusted。Guard/Policy→确定性拦截越界动作。钱包基础设施→Policy Engine 在服务端拦截 + MPC 分布式签名。Simulation→预演结果供 Guard 和 Human Check 决策。失败成本：Policy 内策略失误由用户承担；Policy 外请求自动拒绝无损失。 |
| 4 | **自动化 vs 人工？** | 自动：Policy 内低风险操作（白名单合约固定额度转账、白名单方法重复调用）。人工：中风险需模拟+确认、高风险强制人工确认（超预算、新合约、高危方法、Session Key 首次授权）、超出 Policy 自动拒绝。好的 Human Check 应让用户看懂自己在批准什么（资产变化、权限变化、失败风险），而非一串哈希。 |
| 5 | **如何验证？** | 三层：执行前模拟（预演交易结果与 Policy 参数比对）、发送前确定性拦截（Guard 做规则检查——白名单/限额/方法签名/allowance 异常）、事后审计（链上收据+完整 Audit Trail 记录每次请求和拦截决策）。关键原则：用确定性系统在 Agent 行动前后做独立多层检查，不信任 Agent 的自我报告。 |
| 6 | **落地层？** | 横跨四层：协议/标准层（Account Abstraction + Session Key 标准）、权限系统层（Session Key 生命周期+Policy 引擎）、安全机制层（Simulation + Revocation + MPC + Human Check）、产品层（Cobo Agentic Wallet 是目前最完整实现）。与 Dir1 的区别：Dir1 解决"如何支付"，Dir3 解决"支付时走什么权限通道"。 |
| 7 | **失败原因？** | 最大风险：Policy 的工程折中极难做对——设太宽等于没设，设太窄 Agent 没法用。风险判断（"这个协议安全吗"）是 AI 不擅长的——Agent 可能被恶意合约文档欺骗。其次：用户不愿改变流程（"让 AI 管钱"的心理门槛极高）。最可能的失败：Agent 在用户批准的白名单协议里亏了钱，用户永远不再信任任何 Agent 钱包。 |

### Direction 4：Privacy / Security / Sovereignty
#### 我的判断
两个层次：(1) Security/Privacy——将 AI 安全领域的知识运用在 Web3 场景中，因为上链后不能 rollback，要求更严格；(2) Sovereignty——讨论数据主权问题.Web3可能会向其中引入解决数据主权问题的解决方案.

#### 一句话

AI Agent 接触私钥、用户数据和链上资产，是概率系统——可被 Prompt Injection、恶意文档、工具返回值诱导越权执行。传统 AI 安全解决"外部攻击"；Sovereignty 解决"平台锁定"——没有它，再安全的 Agent 也只是平台的人质。

#### 三问

- **解决什么真实问题？** Threat model 从资产盘点开始——先列清系统持有什么（私钥、API Key、session token、用户数据、交易权限、预算、敏感文档、治理权限），再列攻击入口。两层具体问题：(1) Security/Privacy — Prompt Injection、Tool Abuse、Key & Secret Exposure、链上公开数据+AI 私有记忆拼接。控制手段：最小权限、只读优先、HITL、allowlist、预算上限、沙箱、日志、模拟执行。(2) Sovereignty — 平台锁定：Agent 的记忆和身份留在平台，模型不可换，数据不可迁移，平台封禁即消失。主权问题的检验标准：用户能否导出数据、更换模型、更换执行环境、撤销授权、在不依赖单一供应商的情况下继续使用核心资产。反例：如果系统要求用户把私钥、全部交易权限和完整上下文都托管给一个黑盒 agent，就必须标为高风险，不应作为默认学习路径。
- **AI 角色？Web3 角色？** AI 是不受信任的概率组件。Web3 提供：(1) 安全防线 — TEE/MPC/Policy/Guard/Simulation；(2) 主权基础设施 — ERC-8004 让身份跨平台、可迁移数据+开源客户端+多模型 fallback+链上审计日志。
- **落地层？** Security/Privacy = 安全机制层（横向渗透）。Sovereignty = 价值底层+产品原则——Data Portability、Model Choice、Local-first 不是技术选型，是产品设计决策。

#### 7 问评估

| # | 问题 | 回答 |
|:-:|------|:----|
| 1 | **没有 AI？** | N/A.这是AI Agent本身的问题. |
| 2 | **没有 Web3？** | Security/Privacy：同样成立，但错误上链无法回滚。引入Web3的思想, 为sovereignty提供解决方案. |
| 3 | **角色分配？** | 用户→设定安全策略、处理告警、保留数据导出权。Agent→在边界内执行，输出被视为 untrusted。TEE/MPC/Policy→安全防线。平台→提供多模型切换、身份可迁移、Local-first 选项 |
| 4 | **自动化 vs 人工？** | 自动：TEE(trusted execution environment) 推理、Policy 内操作、zkML 验证。人工：Policy 规则设定、高风险告警审核、模型切换后的高风险验证、数据导出/迁移确认 |
| 5 | **如何验证？** | 技术层：TEE 远程证明+zkML 证明+Audit Trail。主权层：CROPS 检查——身份抗审查吗？关键组件开源吗？数据可导出吗？权限可撤销吗？有关数据主权的内容,人类可查看 |
| 6 | **落地层？** | 隐私计算基础设施层（TEE/MPC）+ 安全机制层（Policy/Guard）+ 主权设计原则（Data Portability/Model Choice/Censorship Resistance）。Security 防攻击，Sovereignty 防锁定 |
| 7 | **失败原因？** | Security：成本过高（TEE 性能损耗、zkML 证明生成慢）。Sovereignty：**用户不愿付出摩擦成本**——习惯了便利，不愿为 Portability/Self-custody 牺牲体验 |

#### 三层拆解

| 层 | 防什么 | 传统 AI 有吗？ | 独特在哪 |
|:---|:------|:-------------:|:---------|
| **Security** | Prompt Injection、Tool Abuse、Key Safety | ✅ 有 | Web3 侧：上链后无法回滚，错误成本更高 |
| **Privacy** | Data Boundary、Minimal Disclosure、Secret Mgmt | ⚠️ 有但弱 | Web3 侧：链上公开数据+AI 私有记忆可被拼接 |
| **Sovereignty** | 平台锁定、无法迁移、Censorship | ⚠️ 问题存在 | **Web3 不是发明了主权问题，是提供了主权问题的解法**——ERC-8004 跨平台身份、可迁移数据、CROPS 抗审查、Self-custody。传统 AI 也有主权需求（你的 prompt/skills/harness 是你自己的），但没有机制保障它

### Direction 5：Dev Tooling / Agent Workflow
#### 我的判断
引入AI解决传统Web3行业的开发问题.一般开发过程中应用的问题在这里仍然适用,并且对Web3涉及真实交易的部分需要着重设定安全边界.
#### 一句话

嵌入工具链的"增强层"——从合约阅读、交易解码、测试生成到部署验证，AI 降低从意图到代码的翻译成本；Agent Workflow（Task Graph + State Machine + Human-in-the-loop）则把 AI 的辅助能力串成可暂停、可审计、可回滚的确定性流程，防止概率模型在高风险链上操作中自由发挥。

#### 三问

- **解决什么真实问题？** Web3 开发认知负担极高：未开源合约的字节码难以逆向理解意图、交易 revert 原因不直观、测试编写耗时且覆盖不全、跨协议交互上下文碎片化。AI 把"读字节码→理解逻辑""看 trace→定位原因""写测试→覆盖边界"的翻译成本大幅降低。Agent Workflow 让 AI 的辅助行为有状态约束和人工断点，而非黑箱输出。
- **AI 角色？Web3 角色？** AI：做上下文理解（自然语言→合约意图）、代码生成（意图→Solidity/测试脚本）、异常解释（revert trace→可读原因）、在 Workflow 中担任计划生成和条件判断。Web3：提供不可替代的数据源（已验证合约、链上数据索引）、执行沙箱（交易模拟预演）、合约标准库（审计后模板）、接口发现能力（从字节码提取 ABI）。
- **落地层？** 开发者工具层（IDE 插件、CLI 助手、CI/CD 集成）+ Agent Workflow 方法论层（Task Graph/State Machine/HITL/Retry/Trace/Eval），以及编排框架层（负责状态管理和工具调用）。关键是区分两个子方向：AI-assisting-developers（工具嵌入）和 AI-becoming-the-developer（Agent 自主执行）。

#### 7 问评估

| # | 问题 | 回答 |
|:-:|------|:----|
| 1 | **没有 AI？** | 仍然成立——Foundry/Hardhat/Tenderly 等工具已是开发者常用的。但没有 AI 时，从"交易 revert"到"根因"的排查靠人工翻 trace，从"需求"到"合约代码"靠经验和模板。AI 消除的不是开发本身，而是中间的翻译和检索成本。 |
| 2 | **没有 Web3？** | N/A.Web3是引入AI工具的目标 |
| 3 | **角色分配？** | 开发者：定义目标、审查 AI 输出、对安全决策做最终确认、设置 HITL 断点。AI Agent：读取合约与交易上下文、生成候选代码/测试/部署脚本、在 Task Graph 中推进步骤并在边界暂停。工具链：提供测试与部署执行环境、模拟沙箱、合约库、数据源。 |
| 4 | **自动化 vs 人工？** | 自动：合约阅读摘要、交易解码、测试生成、gas 优化、文档生成、已知漏洞扫描。人工必须确认：主网合约部署、高危函数调用、安全审计结论、新协议首次交互。原则：只读分析全自动，高风险操作设强制人工断点。 |
| 5 | **如何验证？** | 三层：代码层（AI 生成的代码在模拟环境中实际执行，覆盖率报告确认边界）、分析层（AI 解读用已验证源码和链上状态交叉验证）、流程层（Workflow Trace 记录每步输入/输出/判断理由，Eval Harness 确保修改后不在已知危险场景退化）。 |
| 6 | **落地层？** | 偏向开发者工具层（Visual Auditor 插件、CLI 助手、CI/CD 集成）+ Agent Workflow 方法论层（Task Graph 拆解、State Machine 持久化、HITL 权限边界、Trace 审计）+ 编排框架层。AI-assisting-developers 是渐进改良，AI-becoming-the-developer 必须有 HITL 和 State Machine 才能投产。 |
| 7 | **失败原因？** | 最大风险：AI 生成代码安全性不可靠——看起来正确的 Solidity 可能有漏洞，开发者过度信任直接部署。其次：接口不成熟（Foundry/Hardhat/Tenderly 的 AI 集成度参差不齐）。 |

### Direction 6：Governance / Coordination / Public Goods
#### 我的判断
公共治理问题.不是信息决策, 而是信息整合的加速器.一个方向是从ai本身下手(training / model / agent architecture), 一个方向是harness engineering
#### 一句话

AI 可以帮助 DAO 做提案总结、会议行动项提取、贡献记录追踪、预算审核和 Sybil 检测——让集体决策更高效，但 AI 绝对不能替代人类投票，因为治理是 AI 幻觉社会成本最高的场景。

#### 三问

- **解决什么真实问题？** DAO 治理的信息过载——社区成员面对几十页提案没时间细读，贡献者工作难量化导致薪酬不公，公共物品 funding 靠人工评审无法规模化，Sybil 攻击让一人一票系统失效。
- **AI 角色？Web3 角色？** AI：提案摘要与差异对比、会议纪要转行动项、贡献图谱自动生成、预算合理性检查、Sybil 模式识别、投票趋势分析。Web3：链上治理记录不可篡改、智能合约执行投票结果、去中心化身份防 Sybil、可追溯的公共物品资金流。
- **落地层？** 治理协作层——既有投票框架和 DAO 框架，也有应用层工具（AI 摘要插件、贡献评估、争议仲裁），更有公共物品分配机制。已有 DAO 在探索 AI 辅助治理的边界。

#### 7 问评估

| # | 问题 | 回答 |
|:-:|------|:----|
| 1 | **没有 AI？** | 成立但效率极低——DAO 本来就由人类治理。但信息过载真实存在：数百个项目申请需人工评审，评审疲劳严重影响分配质量。AI 降低的是信息处理成本，不是替代决策本身。 |
| 2 | **没有 Web3？** | Web3本身是管理的目标.投票结果需链上执行不可篡改、公共物品资金需可追溯、Sybil 防御需去中心化身份。没有链上约束，AI 的建议无法触发真正的资源分配。 |
| 3 | **角色分配？** | 贡献者→提交贡献记录/领取 Grant。社区成员→投票决策（最终权在人类）。AI→摘要提案、标注差异、计算贡献权重、标记异常。链上合约→执行投票结果、锁定/释放资金。核心：AI 是顾问，永远不是 voter。 |
| 4 | **自动化 vs 人工？** | 自动：提案摘要生成、贡献数据聚合、Sybil 风险评分、预算模板化审核。人工：最终投票（不可自动化）、争议仲裁、高额资金分配决策、治理框架变更。 |
| 5 | **如何验证？** | AI 摘要可通过原始提案全文对比验证（用另一个 LLM 交叉检查）。贡献记录可通过链上活动自动核实。Sybil 检测可事后通过抓到的假账号验证。关键原则：AI 输出必须可追溯、可复审、可推翻。 |
| 6 | **落地层？** | 治理协作层——架在治理框架之上的智能辅助层。投票基础设施提供底层，AI 插件做摘要分析；贡献评估框架提供基础，AI 做图谱聚合。 |
| 7 | **失败原因？** | 最大风险：信任不可建——社区不信任 AI 摘要准确性（Hallucination 歪曲提案关键点），且 AI 摘要若被治理捕获方操纵将加剧中心化。其次是用户不愿改变流程（DAO 成员习惯靠 KOL 摘要），以及现有工具缺乏 AI 插件标准。 |

### Applied Path：Agent DeFi Execution


#### 一句话

Agent DeFi Execution 是前六个方向的"试金石"——把 Dir1 的 Payment（支付结算）、Dir3 的 Wallet/Permission（权限分层）和 Dir4 的 Privacy/Security（纵深防御）放进一个真实的链上资产执行场景里检验：用户给 Agent 一个投资目标，Agent 在可编程权限边界内完成跨协议的 swap、流动性提供、yield farming，每一步都有模拟预演、确定性拦截和可审计记录。

#### 三问

- **解决什么真实问题？** DeFi 的策略执行窗口极短——最佳 swap 路由、最高 yield 池、最安全的清算线在几分钟内变化，人类无法 7×24 监控响应。Agent 的价值是在用户设定的风险参数内自动抓取机会，同时比人更快、更全面地扫描风险信号。
- **AI 角色？Web3 角色？** AI：理解投资意图→翻译成具体协议选择和仓位配置，实时扫描链上数据，生成候选交易。但它也是概率系统——可能被恶意合约描述欺骗、误判无常损失。Web3：提供可编程权限边界（Pact 定义额度/目标/白名单）、执行前验证（模拟预演+确定性拦截+MEV 保护）、不可篡改的审计记录。
- **落地层？** 端到端应用场景——垂直整合 Dir1 的支付结算+Dir3 的权限系统+Dir4 的安全防御，在 DeFi 协议层之上运行。Pact 定义"做什么、用什么协议、最大金额"，Policy Engine 拦截越界请求，MPC 确保私钥不完整出现。

#### 7 问评估

| # | 问题 | 回答 |
|:-:|------|:----|
| 1 | **没有 AI？** | 仍然成立——人类可以手动操作 DeFi。但 AI 解决三个不可替代的问题：7×24 实时响应（最优窗口活跃在凌晨和周末）、多维度并行扫描（同时追踪 gas/池子深度/预言机价格/健康因子）、意图到策略的翻译（用户说"追求稳定收益"，Agent 判断具体存哪、拆多少比例、什么条件触发再平衡）。AI 消除的是"意图→策略→执行"链路上的人类瓶颈。 |
| 2 | **没有 Web3？** | 传统金融有算法交易和 robo-advisor，但做不到：无需托管（资产始终在 Smart Account 里）、可编程权限粒度（精确到每日限额/协议/池子/slippage）、可组合的策略执行（跨协议操作无需多中介多天结算）、链上审计不可篡改。 |
| 3 | **角色分配？** | 用户→设定 Pact（任务目标、协议白名单、金额上限、风险参数），随时撤销。Agent→在 Pact 范围内读取数据、生成策略、请求执行但不能超出边界。执行层→承载 Session Key 和 Policy Engine，做确定性拦截。Simulator→预演交易结果。MPC→分布式持有私钥。失败成本：超出 Pact 边界自动拒绝无损失；Pact 内策略失误由用户承担。 |
| 4 | **自动化 vs 人工？** | 自动：Pact 内低风险操作（白名单协议 swap、稳定币存取、触发条件再平衡、yield 迁移）。人工：新协议加入白名单、超额大额交易、新 token 类型、Pact 参数修改、异常市场条件自动暂停等人工决策。能写进 Pact 的规则自动执行，需要安全判断的决策必须人工。 |
| 5 | **如何验证？** | 三层：执行前模拟（预演交易结果与 Pact 参数比对）、确定性拦截（Policy Engine 检查白名单/限额/slippage/方法签名）、事后审计（链上收据+完整 Audit Trail）。验证成本中等，但远低于人工逐一审查。原则：用确定性系统在 Agent 行动前后做独立检查。 |
| 6 | **落地层？** | 端到端应用场景层——把 Dir1（支付）+Dir3（权限）+Dir4（安全）垂直整合在 DeFi 协议层之上。技术栈包括权限层（Pact+Session Key+AA）、安全层（Simulation+Guard+MPC）、执行层（DEX/借贷/vault/intent-based 执行）、数据层（RPC+索引+预言机）。与 Dir1 的区别：Dir1 是水管，这个路径是花园灌溉系统。 |
| 7 | **失败原因？** | 最大风险：信任+权限风险的叠加。用户需同时信任 AI 不会在 Pact 边界内做出错误策略、Pact 边界设定足够保守、整个技术栈无实现漏洞——三个条件太容易连锁崩溃。其次：用户不愿改变流程（"让 AI 管钱"的心理门槛极高）。最可能先失败在"Agent 在看似安全的白名单协议上亏了用户的钱"这一场景。 |
